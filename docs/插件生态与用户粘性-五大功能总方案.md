# 插件生态与用户粘性 —— 五大功能总方案

> 版本：v1.0（2026-10-06）
> 定位：基于 andy-harness v1.0.x 现有架构的演进规划，不引入新底层依赖。
> 双目标：① 吸引二次开发者以最小成本扩展；② 让终端用户形成持续使用闭环。

---

## 0. 现有架构盘点（方案可行性的事实依据）

所有方案只复用以下**已存在**的能力，不假设任何未实现的底层设施：

| 能力 | 位置 | 现状 |
|---|---|---|
| 插件内核 | `harness/kernel/loader.py`（PluginLoader / BasePlugin / PluginContext） | 插件 activate/deactivate、ServiceRegistry 注入 |
| 工具契约 | `ToolPlugin`（tool_name / description / risk_level / parameters_schema / execute） | 权限层按 risk_level 管控 + 全量审计 |
| 钩子管线 | `HookManager`：pre/post_context_build、pre/post_model_call、pre/post_tool_call、pre_message_persist | 7 个挂点已全量接入 AgentLoop |
| 事件总线 | `EventBus.publish/subscribe`（现有 topic：`trace.span`、`model.request.delta`） | 异步广播，WS 已旁路消费 |
| Provider 抽象 | `OpenAICompatibleProvider` + ProviderRegistry（DB 持久化 + 加密 Key） | 三家内置 + custom_* 动态注册 |
| 集成抽象 | `IntegrationProvider`（integration_hub：list_actions/authenticate/call/channel） | 飞书已实现 cli/channel/api 三模式 |
| 编排引擎 | `OrchestratorService`（Pipeline/Stage/Subtask + 并行/串行） | 已实现，尚无用户入口 |
| 评测基座 | `tests/evals/eval_cases.json`（expect_keywords/expect_tools/forbid_tools/tags） | 用例格式与判定规则已定义 |
| 定时任务 | scheduled_tasks 表 + REST /api/schedules + runner（AgentLoop 驱动） | 已上线 |
| 可观测 | spans 表 + SpanService + GET /api/traces（含 token 用量/延迟） | 已上线 |
| 会话资产 | fork / export / import（JSON 包，附件物理复制） | 已上线 |
| 市场 | 插件市场（zip 安装）/ 技能市场 / MCP 市场（三套） | 已上线 |
| 前端骨架 | SettingsView 多页签 + AuditLogView + IntegrationsPanel + ProcessTrace + i18n | 页签化扩展成本极低 |
| 数据库迁移 | `CREATE TABLE IF NOT EXISTS` + ALTER 增量升级（database.py） | 加表零成本 |
| 认证 | users 表 + AuthService + require_admin 依赖 | 管理面接口现成 |

## 方案一：插件开发者工作台（Plugin DevKit：脚手架 + 热重载 + 可视化配置）

### 价值定位（一句话）
让二次开发者** 5 分钟内**从模板生成一个能跑的插件，改代码即热重载，配置项自动生成表单——把"读懂内核才能写插件"变成"填表单就能写插件"。

### 目标用户
二次开发者（主）/ 终端用户（配置面板部分）。

### 前后端联动流程

```
前端「设置 → 开发者」页签
  ├─ 选模板（Tool / Provider / Channel / Integration / Hook 五类）
  │    → POST /api/plugins/dev/scaffold {template, id, name}
  │    → 后端按模板渲染到 plugins/<id>/（含 plugin.json、main.py、config.schema.json、_tests/）
  │    → 返回生成文件清单，前端内嵌只读代码预览（引导到本地 IDE 编辑）
  ├─ 保存后点「重载」
  │    → POST /api/plugins/dev/reload/{plugin_id}
  │    → 后端：PluginLoader.deactivate → importlib 重载模块 → activate → 注册表 diff
  │    → 返回 {ok, registered:[tools/providers/hooks], errors:[...]}
  ├─ 实时日志：WS /ws/dev/logs（订阅 EventBus 新 topic `plugin.log`）
  │    → 插件内 ctx.logger.* 自动转发到该 topic
  └─ 可视化配置面板
       → GET /api/plugins/{id}/config-schema（读取 plugin.json 声明的 config.schema.json）
       → 前端按 JSON Schema 自动渲染表单（string/bool/enum/number/secret）
       → PUT /api/plugins/{id}/config → 插件收 deactivate+activate 生效（复用热重载管线）
```

### 扩展点与插件接口定义

1. **manifest 扩展**（plugin.json 新增可选字段，向后兼容）：

```json
{
  "id": "my_tool",
  "config_schema": "config.schema.json",   // JSON Schema，驱动前端表单
  "dev": { "watch": true }                  // 声明支持热重载
}
```

2. **五类脚手架模板**（templates 目录，随包分发）：
   - Tool 模板：实现 `ToolPlugin` 五属性 + execute，自带 `parameters_schema` 示例与权限 risk_level；
   - Provider 模板：继承 `OpenAICompatibleProvider`，演示 default_models / supports_reasoning_content；
   - Channel 模板：实现 `ChannelConnector` 协议（参照 feishu_channel.py 的线程+loop 模式）；
   - Integration 模板：继承 `IntegrationProvider`（list_actions/authenticate/call）；
   - Hook 模板：向 `HookManager` 注册任一挂点，示例改写 ModelRequest。
3. **日志事件**：`EventBus` 新 topic `plugin.log`，PluginContext.logger 统一封装发布。
4. **第三方接入成本**：开发者只需实现一个类 + 一份 manifest，配置/测试/重载/上架全部由平台托管。

### 复杂度与依赖
**中**。依赖：现有 PluginLoader（需补充模块级 reload 与注册表 diff 报告）、插件市场 zip 安装（复用）、JSON Schema 表单渲染（前端手写，约 200 行，无新依赖）。

### 粘性机制
开发者的插件即资产（配置、数据、市场评分都在本平台）；市场安装 → 本地二开 → 提交市场形成闭环，每多一个插件，平台不可替代性上升一分。

## 方案二：个人工作流编排器（Workflow Studio）

### 价值定位（一句话）
把"一次对话能做的事"固化为**可重复运行、可分享、可对比**的多步流水线：用户在可视化界面拼步骤，平台负责调度执行与结果留档。

### 目标用户
二者兼顾（终端用户编排使用；开发者注册自定义步骤类型）。

### 前后端联动流程

```
前端「工作流」页签（复用 scheduled_tasks 编辑器的交互骨架）
  ├─ 步骤编辑器：每步 = {模型, 系统提示词, 用户提示词模板, 允许工具[], 输入引用 ${prev}/${var}}
  │    → POST /api/workflows {id, name, vars_schema, steps[]}
  ├─ 点「运行」：填变量表单（按 vars_schema 渲染，同方案一的 Schema 表单组件）
  │    → POST /api/workflows/{id}/runs {vars}
  │    → 后端 WorkflowRunService：
  │        · 建影子会话（session 复用，标记 workflow 来源）
  │        · 逐 Stage 调 OrchestratorService.run_pipeline（现有引擎）
  │        · 每步发 EventBus topic `workflow.step` {run_id, step, status, span_id}
  │        · 全程 span 落库（trace 页可回放）
  │    → 前端实时进度：WS 推送 workflow.step → 步骤条状态流转
  ├─ 结果页：每步输出卡片 + 变量终值 + 整体 token/耗时（读 spans 聚合）
  └─ 历史对比：GET /api/workflows/{id}/runs → 同一工作流多轮运行并排 diff
```

### 扩展点与插件接口定义

1. **自定义步骤类型**：插件通过 ToolRegistry 暴露的工具天然可被步骤引用（允许工具列表）；另新增可选注册：

```python
class WorkflowStepPlugin(ToolPlugin):
    step_type: str                 # 如 "feishu_create_doc"
    input_schema: dict             # 该步骤的参数 Schema（前端渲染）
    # execute(args) 复用工具契约，返回值自动注入 ${prev}
```

2. **工作流钩子**（HookManager 新挂点，注册方式与现有 7 个挂点完全一致）：
   - `workflow.run.pre` / `workflow.run.post`（整轮）
   - `workflow.step.pre` / `workflow.step.post`（每步，可改写下步输入）
3. **事件**：`workflow.step` topic（进度）+ 既有 `trace.span`（回放）。
4. **分享**：工作流导出为 JSON（与 session export 同构），导入即用。

### 复杂度与依赖
**高**（前端编辑器为主）。依赖：OrchestratorService（已实现）、AgentLoop、spans、scheduled_tasks 编辑器交互模式、方案一的 Schema 表单组件。

### 粘性机制
工作流是用户的"自动化资产"：一次搭建、长期复跑；运行历史 + 对比让用户持续回来验证效果；工作流可分享带来新用户（朋友导入你的工作流就得装本平台）。

## 方案三：评测实验室（Eval Lab：模型 × 提示词 A/B 对比）

### 价值定位（一句话）
同一组问题、多组（模型/系统提示词）组合并排跑分——让"该用哪个模型、提示词改得对不对"从玄学变成看板。

### 目标用户
二者兼顾（终端用户选型；开发者给自己的插件/提示词做回归）。

### 前后端联动流程

```
前端「评测」页签
  ├─ 数据集管理：手动录入 / 从历史会话一键导入提问（GET 会话消息 → 勾选 user 消息 → 存为数据集）
  │    → CRUD /api/evals/datasets（格式对齐现有 eval_cases.json：expect_keywords/expect_tools/forbid_tools）
  ├─ 新建对比：矩阵 = 模型[] × 系统提示词[]（来自会话设置）
  │    → POST /api/evals/runs {dataset_id, matrix}
  │    → 后端 EvalService：
  │        · 每组合 × 每用例建影子会话跑 AgentLoop（allow_tools 按 forbid_tools 注入约束）
  │        · 判定复用 evals 现有规则（关键词/工具命中/禁用工具），输出 pass/fail/detail
  │        · 全程 spans 落库 → token/延迟自动聚合
  │        · 进度经 EventBus topic `eval.progress` → WS 推送
  └─ 结果看板：组合×用例矩阵热力图 + 指标表（通过率/平均延迟/平均 token/估算成本）
       → 历史趋势：同一数据集历次运行曲线（改提示词前后一眼见高下）
```

### 扩展点与插件接口定义

1. **评分插件**（LLM-as-judge / 语义相似度等进阶判定）：

```python
class EvalScorerPlugin(ToolPlugin):
    scorer_id: str                       # 如 "llm_judge"
    def score(self, case: dict, output: str, trace: dict) -> ScoreResult
    # 注册后前端判定规则下拉自动多一项（IntegrationRegistry 同款发现机制）
```

2. **数据集格式**即扩展契约：第三方可发布"领域评测集"（JSON 包），导入即用。
3. 事件：`eval.progress`；复用 `trace.span`。

### 复杂度与依赖
**中**。依赖：evals 判定规则（已存在，从 tests 提升为运行时模块）、AgentLoop、spans 聚合、方案一 Schema 表单（可后置）。

### 粘性机制
换模型、调提示词、升级插件版本后的第一件事就是回来跑一次回归——评测历史成为用户的"质量档案"；分享数据集（如"中文代码助手基准"）形成内容生态。

## 方案四：洞察看板与插件自定义指标（Insights Dashboard）

### 价值定位（一句话）
把散落在 spans/messages/todos/audit 里的运行数据变成一页"个人 AI 使用年报"，且插件可以贡献自己的指标卡——用数据看板养成每日打开的习惯。

### 目标用户
终端用户（主）/ 二次开发者（贡献指标）。

### 前后端联动流程

```
前端「洞察」页（独立路由 /insights，风格对齐 AuditLogView）
  ├─ GET /api/insights/overview?range=7d|30d
  │    → 后端 InsightsService 纯 SQL 聚合现有表：
  │        · 消息量/会话数按日（messages/sessions）
  │        · token 与估算成本按 provider/model（spans）
  │        · 工具调用 Top10 与成功率（spans kind=tool）
  │        · 技能/插件使用分布（spans name 前缀）
  │        · 沙箱/高危操作次数（permission_audit）
  │    → 前端手绘 SVG 图（项目已有 WisdomTree/MatrixRain 自绘先例，零新依赖）
  ├─ 插件指标区：GET /api/insights/plugins
  │    → 平台扫描已注册的 MetricContribPlugin，逐个 collect() 并合并返回
  └─ 数据下钻：卡片点击 → 跳转对应会话 / trace 回放（现有页面深链）
```

### 扩展点与插件接口定义

```python
class MetricContribPlugin(ToolPlugin):
    metric_id: str          # "feishu_docs_created"
    metric_name: str        # "飞书文档创建数"
    def collect(self, since: str, until: str) -> dict:  # {"value": 12, "unit": "篇"}
    # 前端按注册清单自动渲染指标卡；不实现则不出现，零侵入
```

事件：无需新 topic（拉取式）；未来可加 `insights.invalidate` 支持实时刷新。

### 复杂度与依赖
**低**。依赖：仅现有表结构 + ServiceRegistry。是五个方案中唯一"纯聚合"型，无新表（可选加 insights_cache 表做 24h 缓存）。

### 粘性机制
"今天花了多少 token、哪个工具用得最多"是天然的每日回访理由；成本可见性反过来促进用户关注（并续费/配置）更多 Provider；插件指标卡让开发者的插件价值被看见（安装量之外的第二增长回路）。

## 方案五：模板分享中心（Template Hub：提示词 / 技能 / 工作流 / 会话包）

### 价值定位（一句话）
把平台里所有"可复用资产"（角色提示词、技能、工作流、完整会话）统一为一种分享包格式，一键导出、一键导入——让老用户带新用户。

### 目标用户
终端用户（主）/ 二次开发者（分发技能与工作流模板）。

### 前后端联动流程

```
前端「模板库」页签
  ├─ 内置模板区（随包分发的官方模板 JSON）
  ├─ 我的模板：从四处入口打包
  │    · 会话 → 「分享为模板」（复用 export_session，叠加变量占位 {{name}}）
  │    · 会话设置里的系统提示词 → 单独保存
  │    · 技能 / 工作流（方案二产出）→ 导出
  │    → POST /api/templates {type, payload, vars_schema}
  ├─ 使用模板：模板卡 → 预览 → 填变量表单（Schema 渲染）→ 「从模板新建会话」
  │    → POST /api/templates/{id}/instantiate {vars}
  │    → 后端渲染占位符 → 复用 import_session 落库 → 返回新会话 id → 前端切到会话页
  └─ 导入外部包：粘贴/上传 .harness.json → 校验 type 与版本 → 入库为"我的模板"
```

### 扩展点与插件接口定义

1. **分享包格式**（版本化契约，第三方可生成）：

```json
{
  "format": "harness.template",
  "version": 1,
  "type": "session | prompt | skill | workflow",
  "vars_schema": {"type":"object","properties":{"产品名":{"type":"string"}}},
  "payload": { "...": "type 对应的现有导出结构" }
}
```

2. 与三个市场的关系：模板中心面向**用户资产**分发，市场面向**代码资产**（插件/技能/MCP）分发，互为入口（技能市场详情页加"保存为模板"）。
3. 无新 Hook；复用 import/export 管线与 vars_schema 表单组件。

### 复杂度与依赖
**低-中**。依赖：session export/import（已有）、技能市场（已有）、方案一/二的 Schema 表单组件。

### 粘性机制
分享是自增长引擎：用户为让朋友用到自己的模板而留在平台；新用户因一个好模板而装平台；模板收藏数成为用户侧的成就系统。

## 推荐优先级（价值 / 成本比排序）

| 排序 | 方案 | 价值 | 成本 | 比值 | 理由 |
|---|---|---|---|---|---|
| **P0** | 洞察看板（四） | ★★★★ | 低 | **最高** | 纯聚合零新表，1 周内可上线；立即建立每日回访钩子；为后续功能提供共享的图表/深链基建 |
| **P1** | 评测实验室（三） | ★★★★ | 中 | 高 | 判定引擎已存在于 tests/evals，只差运行时化 + 看板；同时服务选型与插件回归两类刚需 |
| **P2** | 插件 DevKit（一） | ★★★★★ | 中 | 高 | 目标一的核心；市场/zip 安装/schema 渲染均有现成件；产出的表单组件被 P3/P4 复用 |
| **P3** | 模板分享中心（五） | ★★★ | 低-中 | 中 | 依赖 P2 的表单组件后成本进一步下降；自增长收益随用户基数放大 |
| **P4** | 工作流编排器（二） | ★★★★★ | 高 | 中 | 粘性天花板最高但编辑器成本大；引擎（Orchestrator）已就绪，等 P0-P2 的基建成熟后启动风险最小 |

**落地节奏建议**：P0 →（P1 ∥ P2，二者无依赖）→ P3 → P4。
**共享基建复用链**：P2 产出的 JSON Schema 表单组件与 `plugin.log` 事件，被 P3（变量表单）、P4（步骤表单/运行变量）直接复用——先做 P2 可让后续每个方案的开发成本下降约 20%。
