## 二、严重 bug（5 项）

### B1. 工具调用被中断 / 被钩子短路时不回填 tool 消息 → 会话永久不可用

- **文件位置**：`backend/harness/engine/agent_loop.py:877`（`_execute_tool_calls`）、`:905`（`short_circuit` 分支）、`:1063`（新增方法）
- **严重程度**：**P0 — 致命**
- **问题与影响**：
  `_execute_tool_calls()` 遍历 tool_calls 时，若中途 `self._stopped` 为真（用户点停止），或 `pre_tool_call` 钩子返回 `short_circuit=True`，代码直接 `continue` / 跳出循环，**不为剩余 tool_call 写入 `role="tool"` 消息**。而 assistant 消息上已经落库了 `tool_calls` 数组。
  结果是会话里残留一条「有 `tool_calls` 但没有对应 tool 响应」的 assistant 消息。DeepSeek / OpenAI 兼容 API 要求：**assistant 消息上的每个 `tool_call_id` 必须有对应的 `role="tool"` 消息**，因此该会话此后**每一次提问都会被 400 拒绝**，会话永久损坏，用户只能删会话重开。
- **修复方式**：
  1. 循环改为 `for index, tc in enumerate(tool_calls)`，在 `if self._stopped` 分支调用新增的 `_backfill_interrupted_tool_calls(tool_calls[index:], session_id)`（`:882`）；
  2. `pre_result.short_circuit` 分支（`:905`）补写 `_persist_message(role="tool", tool_call_id=tc.id, ...)`，不再只 `append` + `continue`；
  3. 新增 `_backfill_interrupted_tool_calls()`（`:1063`）：为每个未执行的 tool_call 落一条 `content="（已被用户中断，未执行）"` 的 tool 消息，保证 tool_call_id 一一对应。
- **验证结果**：`tests/test_regression_fixes.py` 中「中断回填」「短路回填」2 个用例通过；模拟停止后再次请求上下文，tool_call_id 配对完整，会话可持续对话。

### B2. `Message.to_dict()` 丢失 `tool_call_id` → 工具消息失去归属

- **文件位置**：`backend/harness/infra/repository.py:100`（`to_dict`）
- **严重程度**：**P0 — 高**
- **问题与影响**：`to_dict()` 输出的消息字典缺少 `tool_call_id` 字段。REST 返回历史消息、导出会话、分叉会话时，工具结果消息无法与发起它的 `tool_call` 关联，前端无法正确渲染「哪个工具返回了这个结果」，重放上下文时也会破坏 API 要求的配对关系。
- **修复方式**：在 `to_dict()` 返回字典中补 `"tool_call_id": self.tool_call_id`。
- **验证结果**：回归测试断言 `to_dict()["tool_call_id"]` 与消息实例一致；会话导出/分叉流程冒烟通过。

### B3. 权限审计在工具调用热路径上新建 Database 实例 → 连接泄漏 + 性能塌方

- **文件位置**：`backend/harness/modules/permission_manager/audit.py:28`（新增 `_db()`）、`:62`（`record_audit_event`）
- **严重程度**：**P1 — 高**
- **问题与影响**：`record_audit_event()` 每次被调用都 `Database()` 新建实例，而 `Database()` 构造会执行**全量 `init_schema()`**（几十张表的 `CREATE TABLE IF NOT EXISTS`）。每次工具调用至少触发一次，长会话多轮工具调用下造成明显的 I/O 放大与连接/语句对象泄漏。
- **修复方式**：新增按数据库路径缓存的模块级 `_db()`（同路径复用同一 `Database` 实例），`record_audit_event` 改用 `_db().execute(...)`。
- **验证结果**：回归测试连续调用 `record_audit_event` 100 次，`Database` 构造只发生 1 次；审计记录内容正确落库。

### B4. Skill 卸载接口存在路径穿越风险

- **文件位置**：`backend/harness/api/rest/skills.py:63`（新增 `_safe_package_dir`），调用点 `:161`、`:196`、`:217`
- **严重程度**：**P1 — 高（安全）**
- **问题与影响**：安装/卸载技能包时把 `package_id` 直接拼进目标目录并交给 `shutil.rmtree()`。`package_id` 来自用户输入或市场元数据，若含 `../` 或绝对路径，可删除技能目录之外的任意目录。
- **修复方式**：新增 `_safe_package_dir(package_id)`，做**双重校验**：
  1. `package_id` 必须匹配 slug 白名单正则（仅字母数字、`-`、`_`、`.`）；
  2. `dest.resolve().is_relative_to(base)` 确认解析后的真实路径仍在基目录内。
  所有安装/卸载路径构造统一改用该函数。
- **验证结果**：回归测试对 `../evil`、`/etc/passwd`、`..\\win` 等 5 组恶意 id 均被拒绝（返回 400 / 不产生任何删除）。

### B5. 外部包安装 git/HTTP 拉取无超时 + 阻塞事件循环 → 请求永久挂死

- **文件位置**：`backend/harness/modules/package_installer/service.py:91`（`_run_git`，新增 `:1` 处 `DEFAULT_TIMEOUT` 与 `_resolve_timeout`）、`:84`（`_download`）；`backend/harness/api/rest/plugins.py:291-292`、`backend/harness/api/rest/skills.py:183`
- **严重程度**：**P0 — 致命**
- **问题与影响**：分批 `pytest` 时发现 `test_materialize_git_clone_failure` 永远卡在 `git clone` 不动。实证确认：`_run_git()` 调用 `subprocess.run(cmd, check=True, ...)` **无 `timeout`**，而 Windows Git 在源不可达（不存在的本地路径、离线环境、代理 502、私有仓库等待凭据）时会**无限期阻塞**；`_download()` 用 `urllib.request.urlretrieve(url, dest)` 同样**无超时**。更致命的是两个 REST 端点（`POST /api/plugins/install-external`、`POST /api/skills/install-external`）在 `async def` 中**同步**调用 `installer.materialize()`，把阻塞的子进程挂在了事件循环线程上——一旦源不可达，不仅该请求永久挂起，整个 FastAPI 事件循环被占满，**所有请求都不再响应**，服务等同宕机。
- **修复方式**：
  1. `PackageInstaller.__init__(workdir=None, *, timeout=None)` 新增超时参数，默认 `DEFAULT_TIMEOUT=120s`，可用环境变量 `HARNESS_PKG_INSTALL_TIMEOUT` 覆盖；`_resolve_timeout()` 做范围下钳（≥1s）。
  2. `_run_git()`：`subprocess.run(..., timeout=self._timeout, stdin=subprocess.DEVNULL, env={**os.environ, "GIT_TERMINAL_PROMPT":"0"})`，`TimeoutExpired` 转 `RuntimeError`（被 `materialize_git` 捕获为 `"git 拉取失败: ..."`）；`GIT_TERMINAL_PROMPT=0` 防止交互式凭据提示二次挂起。
  3. `_download()`：改用 `urllib.request.urlopen(url, timeout=self._timeout)` + `shutil.copyfileobj` 分块写入，超时受控。
  4. 两个 REST 端点改为 `await asyncio.to_thread(installer.materialize, ...)`，把阻塞调用移出事件循环。
- **验证结果**：新增回归测试 `test_materialize_git_timeout_is_bounded`（设 `timeout=2`），断言 `materialize_git()` 在 ≤30s 内返回失败且 `not res.success`；`test_package_installer.py` 整体 **13 passed in 13.32s**（原先会无限卡死）；`ruff check` + `mypy` 对三个改动文件全绿。

## 三、功能缺口（12 项）

### F1. 删除会话不级联清理 → 孤儿数据与磁盘垃圾永久残留

- **文件位置**：`backend/harness/modules/session_manager/service.py:162`（调用点）、`:165`（新增 `_cleanup_orphans`）；配套 `backend/harness/modules/artifact_store/service.py:152`（新增 `delete_by_session`）
- **严重程度**：**P1 — 高**
- **问题与影响**：SQLite 中 `artifacts`、`agent_runs`、`channel_links`、`memories` **均无外键 `ON DELETE CASCADE`**。删除会话只删了 `sessions` / `messages` 行，其余全部成为孤儿：artifact 的**磁盘大文件永不释放**，渠道映射指向已删会话，会话级记忆永远查不到也删不掉。
- **修复方式**：`delete_session()` 末尾调用新增的 `_cleanup_orphans(session_id)`：
  - `artifacts`：先经 `ArtifactStore.delete_by_session()`（`:152`，逐个 `delete()`，删文件 + 删元数据），再兜底 `DELETE FROM artifacts WHERE session_id=?`；
  - `agent_runs`、`channel_links`、`memories(scope='session')` 依次清理；
  - 各步独立 `try/except`，单步失败不影响其余清理与删除主流程。
- **验证结果**：回归测试中建会话 → 建 artifact（含真实文件）→ 建 run / 映射 / 记忆 → 删除会话，断言四类残留计数均为 0 且磁盘文件已消失。

### F2. 评测数据集删除产生孤儿运行记录，且无删除单条运行的入口

- **文件位置**：`backend/harness/modules/evals_lab/service.py:82`（`delete_dataset`）、`:86`（新增 `delete_run`）；`backend/harness/api/rest/evals_lab.py:141`（新增路由）
- **严重程度**：**P2 — 中**
- **问题与影响**：删除 dataset 只删数据集行，`eval_runs` 里引用它的运行记录成为孤儿，统计与列表页会出现无主数据；同时系统**完全没有**删除单条运行记录的 API，失败的脏运行无法清理。
- **修复方式**：`delete_dataset()` 先执行 `DELETE FROM eval_runs WHERE dataset_id = ?` 再删数据集；新增 `delete_run(run_id) -> bool`；新增 REST 路由 `DELETE /runs/{run_id}`，不存在返回 404。
- **验证结果**：冒烟脚本 `[7]` 步骤验证「删除不存在的评测运行 → 404」；回归测试验证删数据集后 `eval_runs` 计数归零。

### F3. 一次性定时任务 `run_at` 缺失 / 格式错误 / 已过期时仍创建成功却永不执行

- **文件位置**：`backend/harness/modules/scheduler/service.py:353`（新增 `validate_schedule`）、`:376`（`create_task` 调用）、`:417`（`update_task` 调用）；`backend/harness/api/rest/schedules.py:185`、`:197`
- **严重程度**：**P2 — 中**
- **问题与影响**：`once` 类型任务若未提供 `run_at`、格式非法或时间已过，创建接口照常返回 200，任务静默入库后**永远不会被触发**，且界面无任何提示，用户以为已排程。
- **修复方式**：新增静态方法 `validate_schedule(spec, *, enabled=True)`，对 `once` 类型校验：缺 `run_at` → 抛 `ValueError`；解析失败 → 抛 `ValueError`；时间早于当前 → 抛 `ValueError`。`create_task()` / `update_task()` 调用校验；REST 层捕获 `ValueError` 转 `APIError("SCHEDULE_INVALID", str(e), 400)`。
- **验证结果**：冒烟脚本 `[5]` 步骤验证「一次性任务缺 run_at → 400」；回归测试覆盖三种非法输入均被拒。

### F4. MCP 多路径配置只取第一个命中文件，其余被整体丢弃

- **文件位置**：`backend/harness/modules/mcp_client/service.py:674`（`load_config`）
- **严重程度**：**P2 — 中**
- **问题与影响**：`load_config()` 遍历配置路径时，一旦某个文件存在就 `return`，且进入循环前 `self._configs.clear()`。若用户级 `mcp.json` 存在，**项目内置的 MCP server 被整体丢弃**，前端只能看到用户配置；反之亦然。多来源配置无法共存。
- **修复方式**：改为**多路径合并**：移除 `self._configs.clear()` 与提前 `return`，遍历所有路径逐份合并，同名 server 以后续（更高优先级）路径为准。
- **验证结果**：回归测试构造两个各含 1 个不同 server 的配置文件，断言 `load_config()` 返回 2 个；同名冲突时取高优先级那份。

### F5. MCP 删除不存在的 server 返回 200；同名新增静默覆盖已有配置

- **文件位置**：`backend/harness/modules/mcp_client/service.py:757`（`add_server`）、`:776`（`remove_server`）；`backend/harness/api/rest/mcp.py:137`、`:242`
- **严重程度**：**P2 — 中（契约失真）**
- **问题与影响**：`DELETE /servers/{name}` 对不存在的 name 也返回成功，前端无法区分「删掉了」和「本来就没有」，幂等语义错误；`add_server()` 对同名配置直接静默覆盖，用户手改的配置会被无声替换。
- **修复方式**：`add_server(cfg, *, overwrite=False)` 在同名配置已存在且未显式 `overwrite=True` 时抛 `RuntimeError`；`remove_server()` 返回 `bool` 表示是否真实删除；REST 层 `DELETE` 前置 `if name not in svc.get_configs()` → 404。
- **验证结果**：冒烟脚本 `[4]` 步骤验证「删除不存在的 MCP server → 404」；回归测试验证重复新增抛错、显式 overwrite 才覆盖。

### F6. 工作流成功运行不写 `finished_at`

- **文件位置**：`backend/harness/modules/workflows/service.py:128`
- **严重程度**：**P2 — 中**
- **问题与影响**：成功分支的 UPDATE 只写 `status` / `steps_json`，**只有异常分支**（`:161`）写 `finished_at`。因此所有成功运行记录的 `finished_at` 恒为 `NULL`，运行时长统计、耗时趋势、最近完成时间等全部不可用。
- **修复方式**：成功分支 UPDATE 增加 `finished_at = ?` 并传入当前时间。
- **验证结果**：回归测试运行一次成功工作流，断言 `finished_at` 非 NULL。

### F7. Insights 插件指标扩展点从未接线 → `/api/insights/plugins` 恒返回 `[]`

- **文件位置**：`backend/harness/modules/insights/builtin_metrics.py`（新建，`:190` `register_builtin_contributors`）；`backend/harness/main.py:175-177`

### F8. 渠道会话映射指向已删会话且无自愈

- **文件位置**：`backend/harness/modules/channel_manager/service.py:247`（`_resolve_session`），调用点 `:202`
- **严重程度**：**P2 — 中**
- **问题与影响**：渠道 ↔ 会话映射持久化在 `channel_links`。若会话被删除，映射行仍存在，`_resolve_session()` 直接复用映射里的 `session_id`，导致渠道消息**写入一个不存在的会话**（消息丢失或异常）。
- **修复方式**：`_resolve_session()` 增加存在性校验：映射指向的会话若已不存在，先清理该失效映射，再走新建会话分支。
- **验证结果**：回归测试模拟「建映射 → 删会话 → 再来消息」，断言自动重建会话且消息正常落库，无异常。

### F9. `resume_run` 执行失败仍标记 `resumed`

- **文件位置**：`backend/harness/engine/checkpoint.py:210`
- **严重程度**：**P2 — 中**
- **问题与影响**：`resume_run()` 结尾无条件 `update_status(run_id, "resumed")`。若续跑本身失败（模型调用报错、上下文重建失败），运行记录被标成 `resumed`，**失败被伪装成成功**，重试与状态展示全部失真。
- **修复方式**：改为 `update_status(run_id, "error" if result.error else "resumed")`。
- **验证结果**：回归测试构造 `result.error` 非空的续跑，断言状态为 `error` 而非 `resumed`。

### F10. `skipped` 被计为失败 → 失败率虚高

- **文件位置**：`backend/harness/modules/scheduler/service.py:525-530`（`record_task_result`）
- **严重程度**：**P2 — 中**
- **问题与影响**：`record_task_result()` 对 `status == "skipped"` 走了 `fail_count + 1` 分支。任务被跳过（如并发限流、条件不满足）并非执行失败，却计入失败次数，导致任务失败率虚高、自动禁用策略被误触发。
- **修复方式**：`skipped` 分支改为 `fail_count = task.fail_count`（不递增），仅真正失败才 `+1`。
- **验证结果**：回归测试连续记录 3 次 skipped，断言 `fail_count` 保持 0；记录 1 次 failure 后为 1。

### F11. 模板实例化时会话服务缺失返回 500（应为 503）

- **文件位置**：`backend/harness/modules/templates_hub/service.py:186-188`
- **严重程度**：**P3 — 低**
- **问题与影响**：`session_manager` 未就绪时抛 `RuntimeError`，全局异常处理器映射为 **500 Internal Server Error**。这是依赖服务未就绪，语义上应为 **503 Service Unavailable**，500 会污染错误告警与 SLO 统计。
- **修复方式**：改为 `raise ServiceUnavailable("session_manager")`（补 `from harness.kernel.exceptions import ServiceUnavailable`，`:21`）。
- **验证结果**：回归测试在未注册 `session_manager` 的情况下实例化模板，断言 HTTP 503 而非 500。

### F12. 自动总结记忆无 `user_id` → 启用认证后永久不可见

- **文件位置**：`backend/harness/modules/memory_manager/summarizer.py:232`
- **严重程度**：**P2 — 中**
- **问题与影响**：自动记忆总结调用 `self._memory.save(...)` 时未传 `user_id`，记忆以 `user_id=''` 落库。而 `list` / `search` / `render_hint` 全部按当前用户 `user_id` 过滤 —— **开启认证后，自动总结出来的记忆永远查不出来**，等于功能失效。
- **修复方式**：`save()` 增加 `user_id=str(getattr(session, "user_id", "") or "")`，继承会话归属用户。
- **验证结果**：回归测试用带 `user_id` 的会话触发总结，断言落库记忆的 `user_id` 与会话一致且可被该用户检索到。

## 四、前后端联动失效（3 项）

### C1. 流式生成途中切换会话 → 新会话被锁死 + 旧答案串显

- **文件位置**：`frontend/src/stores/chat.ts:32`（新增 `streamingSessionId`）、`:231-232`（跨会话帧过滤）、`:158`、`:701`
- **严重程度**：**P1 — 高**
- **问题与影响**：`isStreaming` 是全局单一状态，**没有归属会话的概念**。A 会话还在流式输出时切到 B 会话，B 的 `isStreaming` 仍为 `true` → **输入框与发送按钮被禁用**，用户要等 A 回答完才能操作；同时 A 的后续 `token_delta` 帧会被追加到 B 的消息列表上，造成**跨会话串显**。
- **修复方式**：
  1. 新增 `streamingSessionId` ref，标记当前流式回答归属哪个会话；
  2. `sendMessage()`（`:411`）/ `regenerateAnswer()`（`:485`）开始时写入 `streamingSessionId.value = sessionId`；
  3. `handleWSFrame()`（`:231-232`）开头增加跨会话帧过滤：当 `streamingSessionId !== currentSessionId` 且帧类型为 `token_delta` / `tool_event` / `done` 时直接丢弃；
  4. `error` / `done` / `stopStreaming` / 模拟流完成等所有出口分支清空 `streamingSessionId`（`:276`、`:281`、`:376`、`:443`、`:514`、`:549`、`:600`）；
  5. `selectSession()`（`:155-162`）切换会话时重置 `isStreaming=false`、`regeneratingParentId=null`、`streamingSessionId=null`、`error=null`，并清理 `mockTimer`。
- **验证结果**：前端 vitest 57/57 通过；`vue-tsc` 无错误；手动验证切换会话后新会话可立即输入、旧会话答案不再串显。

### C2. `sendMessage` 发送失败后未撤销乐观状态 → 界面永久锁死

- **文件位置**：`frontend/src/stores/chat.ts:411`（乐观置位）、`:443`（失败撤销）
- **严重程度**：**P0 — 致命**
- **问题与影响**：`sendMessage()` 先把 `isStreaming` 置 `true` 并乐观插入用户消息，随后 `ws.send()` 返回 `false`（连接断开 / 未就绪）时**直接 `return`，不复位任何状态**。结果是 `isStreaming` 永久为 `true`，**输入框和发送按钮永久禁用**，用户不刷新页面就再也发不出消息。
- **修复方式**：发送失败分支增加完整的乐观状态撤销：清空 `streamingSessionId`、复位 `isStreaming=false`、弹出错误提示，并移除/回滚已插入的乐观消息。`regenerateAnswer()`（`:485`、`:513-515`）同步补齐相同处理。
- **验证结果**：回归/单测覆盖 `ws.send` 返回 false 的路径，断言 `isStreaming` 回落为 `false`、`streamingSessionId` 为 `null`，界面可继续发送。

### C3. `regeneratingParentId` 在停止 / 看门狗超时 / 切换会话后残留

- **文件位置**：`frontend/src/stores/chat.ts:22`（定义）、`:157`、`:275`、`:280`、`:548`、`:494`、`:513`
- **严重程度**：**P2 — 中**
- **问题与影响**：`regeneratingParentId` 标记「正在重新生成第 N 版答案」，但在用户主动停止、看门狗超时、切换会话等路径上**没有清理**。残留后，下一条普通提问会被误判为重回答，消息被挂到旧的 `parent_id` 下，版本分组错乱（表现为消息树层级异常、`‹ 第 i/N 版 ›` 切换器出现在不该出现的位置）。
- **修复方式**：在 `stopStreaming`（`:599-600` 附近）、看门狗超时分支、`error` / `done` 分支、`selectSession()`（`:157`）统一复位 `regeneratingParentId = null`；`regenerateAnswer()` 正常置位（`:494`）与失败撤销（`:513`）成对出现。
- **验证结果**：前端单测覆盖停止 / 超时 / 切换会话三条路径，断言 `regeneratingParentId` 均为 `null`；版本分组恢复正常。
