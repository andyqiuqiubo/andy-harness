## 三、P0 问题清单（阻塞级，必须立即修复）

### P0-1 录制回放会话 ID 路径穿越 -> 任意目录删除（已实证）

| 项 | 内容 |
|----|------|
| **位置** | `backend/harness/api/rest/desktop_repeat.py:197`（DELETE 路由） -> `backend/harness/modules/desktop_repeat/service.py:462-468`（delete_session） |
| **严重级别** | **P0（已实证可利用）** |
| **触发条件** | `DELETE /api/desktop-repeat/sessions/{sid}`，sid 取值为 `..` 或 `../<任意目录名>` |

**证据（PoC 已实跑）**

```python
parent = Path(tempfile.mkdtemp())
root   = parent / "sessions"; root.mkdir()
victim = parent / "victim";    victim.mkdir()
(victim / "important.txt").write_text("DO NOT DELETE")

target = root / "../victim"
# -> resolved: <parent>/victim
# -> victim/important.txt 经穿越可达: True
shutil.rmtree(target, ignore_errors=True)
# -> after rmtree, victim dir still exists: False   <- 目录被真实删除

**原因链**

1. REST 层 `desktop_repeat.py:197` 的 `sid: str` 是裸 str 类型，没有 Pydantic 路径约束（对比同项目 `reverse_engineering.py` 的 `run_id` 走 `_validate_run_id` 白名单）。
2. Starlette/FastAPI 的路径参数正则是 `[^/]+`，`..` 与 `%2e%2e` 都能匹配。
3. 服务层 `service.py:462` 直接 `sdir = self._root / session_id`，未做 `resolve()` + `is_relative_to()` 校验。
4. `service.py:468` 执行 `shutil.rmtree(sdir, ignore_errors=True)`，无根目录边界检查。
5. `ignore_errors=True` 还会吞掉所有异常，目标不存在也不报错，调用方无法察觉。

**影响**

- 认证开启时需管理员 token，风险面收窄；认证未启用时（项目默认单用户模式）任何本地/局域网请求方可触发。
- 破坏面可达 `sessions_root` 的任意父级目录（`..` 向上逐层）。
- 同一缺陷也存在于读路径：`get_session`（`service.py:443`、`456-457`）、`compile_session`（`service.py:476`）、`vision_status`（`service.py:561`）可读取并回传 `sessions_root` 之外的任意 `session.json` 内容。
- 附带 `ignore_errors=True` 使失败静默，难以在日志中发现攻击痕迹。

**修复建议**

```python
# service.py 新增统一入口，所有涉及 sid 的路径拼接都必须走它
import re
_SID_RE = re.compile(r"^r-[0-9a-f]{6,32}$")   # 与 store/bundle.new_session_id() 的形态对齐

def _session_dir(self, sid: str) -> Path:
    if not isinstance(sid, str) or not _SID_RE.match(sid):
        raise RepeatError("RP-6001", f"非法会话 ID: {sid!r}", 400)
    d = (self._root / sid).resolve()
    if not d.is_relative_to(self._root.resolve()):
        raise RepeatError("RP-6001", "会话路径越界", 400)
    return d
```

- `delete_session` 改用 `_session_dir(sid)`，并把 `shutil.rmtree(..., ignore_errors=True)` 改为 `ignore_errors=False` + 显式 `except OSError` 记日志。
- REST 层增加 `sid: str = Path(..., pattern=r"^r-[0-9a-f]{6,32}$")` 双保险。
- 补测试：`test_desktop_repeat_api.py` 增加 `DELETE /sessions/..`、`DELETE /sessions/../x` 两个用例，断言 4xx 且目标目录仍存在。
- **验收标准**：PoC 脚本重跑，输出 `after rmtree, victim dir still exists: True`。

### P0-2 录制器子进程透传宿主机完整环境变量

| 项 | 内容 |
|----|------|
| **位置** | `backend/harness/modules/desktop_repeat/service.py:212-230`（`_spawn_recorder`） |
| **严重级别** | **P0（违反项目明文安全红线）** |
| **证据行** | `service.py:218`：`"env": {**dict(__import__("os").environ), "PYTHONIOENCODING": "utf-8", "PYTHONUTF8": "1"}` |

**原因**

录制器子进程（`python -m harness.modules.desktop_repeat.recorder.runner`）需要的环境变量极少——它只需要 `PATH`、编码设置和 `HARNESS_*` 系列配置。但当前实现把**后端进程的全部环境变量**原样复制过去。

**影响**

- 后端进程环境中的敏感凭据（模型 Provider API Key、`DASHSCOPE_API_KEY`、数据库口令、代理凭据、`HARNESS_KB_ASR_API_KEY` 等）全部进入子进程环境。
- 子进程是**用户态同权限**进程，正常情况下不会主动外泄；但一旦录制器崩溃时把环境 dump 到日志（`recorder.log` 走 `stdout/stderr` 重定向，见 `service.py:214-216`），或被第三方依赖读取，密钥即落盘。
- 这**直接违反** `AGENTS.md` 安全红线一节：「**禁止**在子进程中透传完整 `os.environ`（参考 `sandbox_manager`）」。
- 同项目 `reverse_engineering/stages.py:1258-1264` 的沙箱子进程已正确实现了环境白名单（只放 `PATH`/`SYSTEMROOT`/`TEMP`/`TMP`），**同一仓库内两套标准不一致**。

**修复建议**

```python
# service.py:212 _spawn_recorder 内改为显式白名单
def _recorder_env(self) -> dict[str, str]:
    allow = ("PATH", "SYSTEMROOT", "WINDIR", "TEMP", "TMP", "USERPROFILE",
             "APPDATA", "LOCALAPPDATA", "HOMEDRIVE", "HOMEPATH", "LANG")
    env = {k: os.environ[k] for k in allow if k in os.environ}
    # 项目自定义配置按前缀白名单放行
    for k, v in os.environ.items():
        if k.startswith("HARNESS_REPEAT_"):
            env[k] = v
    env.update({"PYTHONIOENCODING": "utf-8", "PYTHONUTF8": "1"})
    return env
```

- **验收标准**：`grep -n "os.environ" harness/modules/desktop_repeat/service.py` 不再出现整体透传。

## 四、P1 问题清单（高优先级，本轮迭代内修复）

### P1-1 安全门默认策略对高风险动作免审

- **位置**：`backend/harness/modules/desktop_repeat/config.py`（`approval_policy: str = "never"`）、`backend/harness/modules/desktop_repeat/safety_gate.py:54`、`:87-109`
- **现象**：`RepeatConfig.approval_policy` 默认 `"never"`；`config.py` 的加载逻辑里 `pol if pol in (...) else "never"` —— 任何非法配置值都静默回落为最宽松的 `never`。`SafetyGate` 在 `never` 策略下对 `dangerous` 级动作直接 `allow`（`safety_gate.py:107-109`），仅留审计痕迹。
- **影响**：项目文档宣称的「dangerous 每次确认」「密码字段禁止自动回放」等安全承诺，在默认配置下全部不生效。`SafetyGate.risk_of`（`:60-61`）对未知动作的默认值是 `"write"` 而非 `"dangerous"`，进一步放宽。
- **建议**：
  1. 默认值改为 `"degraded"`（仅降级定位的写操作需确认），把 `"never"` 降级为需显式 opt-in 的选项；
  2. 配置解析对非法值显式报错或回落 `degraded`，不要回落 `never`；
  3. `SafetyGate.risk_of` 的未知动作默认值改为 `"dangerous"`；
  4. 启动时在 `status()` 输出当前 `approval_policy` 并在 REST `/status` 暴露，前端明示。

### P1-2 知识库 DOCX 解析无解压炸弹防护

- **位置**：`backend/harness/modules/knowledge_base/parsers.py:130-192`（`parse_docx`）
- **现象**：`zipfile.ZipFile(_BytesReader(data))` 后逐个 `zf.read(media_path)`，没有对 `ZipInfo.file_size` 做总量/条目数上限校验；`zf.read()` 会一次性把整个成员读入内存。
- **影响**：上传一个几百 KB 的构造 zip（压缩比可达 1000:1）即可让服务端内存暴涨到 GB 级，触发 OOM。同文件 `parsers.py:265-290` 的 PDF 解析对 `zlib.decompress(raw)` 也无输出上限校验，是同构问题。
- **建议**：
  1. 解析前统计 `sum(i.file_size for i in zf.infolist())`，超过阈值（建议 100 MB）直接抛 `ParseError`；

### P1-3 逆向 jar 解包无解压量上限防护

- **位置**：`backend/harness/modules/reverse_engineering/stages.py:2017-2024`（`_extract_jars`）
- **现象**：`zf.extractall(out_dir)`。Python 的 `extractall` 自 3.6.12 起已修复 `..` 穿越（抛 `ValueError`），但完全没有解压量上限：FernFlower 产出的 jar 若异常膨胀，同样是内存/磁盘炸弹。
- **附注**：`except zipfile.BadZipFile: continue` 只捕获 `BadZipFile`，`ValueError`（路径穿越）会向上冒泡，导致整个阶段 FAILED 而非降级。
- **建议**：
  1. 改用逐成员 `zf.open()` + 手动写盘，统计解压后总字节数，超阈值中断；
  2. 显式校验每个成员名 `Path(name).resolve().is_relative_to(out_dir.resolve())`；
  3. `except (zipfile.BadZipFile, ValueError, OSError)` 统一降级为 continue + 记日志。

### P1-4 知识库 Embedding/Rerank 端点未走 SSRF 校验

- **位置**：`backend/harness/modules/knowledge_base/embedding.py:97-99`、`:156-167`；`backend/harness/modules/knowledge_base/adapters.py:79-82`
- **现象**：`httpx.AsyncClient().post(url, ...)` 中 `url = f"{self.endpoint}{path}"`，`endpoint` 由用户在 `POST /api/kb/embedding-models` 提交并存储，全程没有调用 `harness.infra.net_guard.assert_url_safe`。
- **影响**：管理员可把 endpoint 指向 `http://127.0.0.1:8000/...`、`http://169.254.169.254/...`（云元数据）等内网地址，以服务端身份发起请求，构成 SSRF。响应体会通过 `EmbeddingError(f"...{resp.text[:200]}")` 回显，形成信息回传通道。
- **对照**：`AGENTS.md` 安全红线明确「禁止未校验的 URL 直接进入 urlopen / httpx 请求」，且 `infra/net_guard.py` 已提供现成护栏。
- **建议**：在 `EmbeddingClient.__init__` / `RerankClient.__init__` / ASR adapter 构造时调用 `net_guard.assert_url_safe(endpoint)`；对用户自建的内网端点提供显式 allowlist 开关。

### P1-5 录制回放 REST 会话 ID 全线无白名单（读路径越权读取）

- **位置**：`backend/harness/api/rest/desktop_repeat.py:190`、`:225`、`:232`、`:174`；服务层 `service.py:443`、`476`、`561`
- **现象**：与 P0-1 同源，此处聚焦读取侧：`get_session` / `vision_status` / `compile_session` 均用 `self._root / sid` 拼接后直接读文件。
- **影响**：可读取 `sessions_root` 之外的任意 `session.json`（若攻击者能先在目标位置放置文件，则可外泄其内容），并且 `compile_session` 会进一步调用 `reader.verify()` 触发对外部目录的 manifest 校验与哈希计算。
- **建议**：与 P0-1 共用同一个 `_session_dir()` 守卫，一次性封堵读写两侧。

### P1-6 逆向子进程继承宿主机完整环境（java/javap/反编译器）

- **位置**：`backend/harness/modules/reverse_engineering/stages.py:1875-1877`、`:1957-1964`；`backend/harness/modules/reverse_engineering/rebuild.py:130-137`

### P1-7 知识库 build_vectors 向量数量不匹配被静默吞掉

- **位置**：`backend/harness/modules/knowledge_base/service.py`（`build_vectors` 内 `vectors = await client.embed(texts)` 与 `zip(segs, vectors, strict=False)`）
- **现象**：`EmbeddingClient.embed` 内部按 `self.batch_size` 分批（`embedding.py:113-126`），但客户端在某批失败或返回条目数偏少时**只返回短列表，不抛异常**；`build_vectors` 用 `zip(..., strict=False)` 组合，长度不等被静默吞掉。
- **影响**：向量索引出现空洞，部分分段没有向量却仍被计入 `embedded` 计数，且 `index_type` 仍被置为 `"both"`。用户看到「重建成功」，语义检索却静默漏召回，**无任何错误信号**。
- **建议**：
  1. `zip(segs, vectors)` 去掉 `strict=False`，数量不等即抛 `KBServiceError`；
  2. `embedded` 计数改为实际写入成功数；
  3. 客户端 `embed`（`embedding.py:108-127`）补齐长度校验：每批返回条目数与入参不等即抛 `EmbeddingError`。

### P1-8 知识库 search_semantic 全表扫描 + Python 循环

- **位置**：`backend/harness/modules/knowledge_base/retrieval.py:98-120`
- **现象**：`SELECT ... FROM kb_segments WHERE embedding IS NOT NULL` 无 LIMIT，取出全库向量后在 Python 里逐条 `np.dot` 计算并排序。
- **影响**：分段量达到数万级时，单次语义检索会拉取全库向量进内存并做 O(N) 循环。该函数是同步的，被 `retrieve()` 直接调用（`retrieval.py:185`、`:204`），**阻塞事件循环**。这是知识库唯一的性能悬崖。
- **建议**：
  1. 用 numpy 矩阵化计算（`np.stack` + `matrix @ q`）替代 Python 循环；
  2. 或引入 sqlite-vec / FAISS 等 ANN 索引；
  3. 短期兜底：给检索加 LIMIT 上限 + 分库分片。

### P1-9 录制回放 run 失败路径未保证释放输入设备租约

- **位置**：`backend/harness/modules/desktop_repeat/service.py:663-707`、`:774`（`_run_and_persist`）、`:821`（`_cleanup_run`）
- **现象**：`lease.acquire()` 成功（`:664-668`）后，`asyncio.create_task(self._run_and_persist(run_id, runner))`（`:701`）启动的后台任务若在 `runner.run()` 抛出未捕获异常，**没有任何 `finally` 保证 `_release_lease()` 被调用**。
- **影响**：输入设备租约（`Global\andy_repeat_input` 全局互斥锁）被永久占用，此后**所有录制与回放都被 `RP-5004` 拒绝**，只能重启后端恢复。这是典型的「一次异常 → 整个功能不可用」故障模式。
- **附注**：`:669-681` 的 `except RepeatError` 分支中，RP-8001/8002/8003 走 `return` 前已释放，fall-through 分支 `:680` 又调一次 `self._release_lease()`（因 `:435` 有 `if self._lease is not None` 守卫，幂等，不会崩，但属逻辑重复）。
- **建议**：用 `try/finally` 包裹 run 生命周期，把 `_release_lease()` 放进 `finally`；`_cleanup_run` 中一并调用，并补一个「run 内部异常后租约仍可再次获取」的测试。

## 十、结论

### 10.1 客观评价

这三个模块的**设计水平明显高于一般同类项目**：降级哲学、崩溃收敛、原子写、进度非阻塞、脱敏链路、Evidence v2 哈希链等细节都做到了位，注释里大量记录了"历史缺陷"与"真机坐实"的实证过程，说明是真实迭代出来的代码而非 AI 拼凑。

**但工程化的最后一公里存在硬伤**：录制回放模块作为**唯一会真实操作用户桌面、注入鼠标键盘、删除文件**的模块，恰恰是安全防护最薄弱的那个——路径穿越可删任意目录（已实证）、子进程环境全量透传、安全门默认免审。这三条叠加，构成一条完整的攻击链：

```
路径穿越（读 sessions_root 外的 session.json）
        ↓  拿到 flow graph
        ↓  以管理员身份 POST /runs 启动回放
        ↓  approval_policy 默认 never（无人工确认）
        ↓  回放执行 flow 中的 dangerous 动作
        ↓  目标 = 用户桌面
```

知识库与逆向模块的问题性质不同：没有"可被直接利用"的链，主要是**资源耗尽（解压炸弹）、内网探测（SSRF）、规模上限缺失**这类"规模上去就出事"的隐患，且都有现成的项目内解法（`net_guard`、`limits.py` 的上限约定）只是没接上。

### 10.2 修复后的预期健康度

|------|------|--------------|--------------|
| 知识库 | B | B+ | A- |
| 工程强逆向 | B+ | A- | A |
| 录制与回放 | C+ | B | B+ |

### 10.3 给下一轮的关键建议

1. **把"路径参数白名单"变成框架级约定**。本次 P0-1 与 P1-5 的根因是同一个：手写路径拼接。逆向模块做对了（`_validate_run_id` + `_RUN_ID_RE`），录制回放没做。建议在 `AGENTS.md` 中明确"所有路径参数必须走统一守卫"，并在 `infra/` 提供 `safe_join(root, *parts)` 工具函数。
2. **把"子进程 env 白名单"变成基建**。项目里已经有两套正确实现（`sandbox_manager`、`reverse_engineering` 的 `_run_isolated`）和三套遗漏（录制器、javap/反编译器、rebuild）。抽到 `infra/subproc.py` 一处，四处共用。
3. **为安全关键默认值加测试**。`approval_policy` 这类"默认放宽"的配置项，恰恰是最该有断言保护的——一句 `assert cfg.approval_policy != "never"` 就能防住 P1-1。
4. **把门禁纳入 CI 硬门槛**。本次实测 `ruff` 5 处、`mypy strict` 4 处违规能在 `main` 分支存活，说明门禁要么没跑、要么没卡住。`AGENTS.md` 已有 `Makefile` 检查目标，接到 pre-commit / CI 上即可。

`service.py:583` 在函数内部 `from harness.main import _services`。这让 `modules/` 层依赖了应用装配层，破坏 AGENTS.md 定义的「kernel 装配 → modules 实现」单向依赖。虽然用了延迟 import 规避循环，但耦合依然存在（P3-3）。

- `stages.py:28` / `rebuild.py` 依赖 `evidence_v2.service.sha256_file` / `sha256_bytes`。
- 耦合合理，模块边界清晰。

**（4）`desktop_repeat` 与 `workflows` 双向依赖**

- `workflows/engine.py:224` 反向 import `desktop_repeat.service`（gui 节点分派）。
- `desktop_repeat/service.py:597-599` 调 `workflow_service.create_workflow` / `update_workflow`。
- 构成**双向依赖**（workflows → desktop_repeat → workflows）。目前靠 `Any` 类型 + 延迟 import 维持，但类型系统无法给出任何保护。

### 7.3 三模块的共同优点（值得保留并推广）

1. **降级优先的设计哲学**：逆向的 `ok/degraded/failed` 三态、知识库的 `degraded=True` + `warn` 标记、录制回放的 `SUBSTITUTED` 阶段状态——都做到了"能力缺失不阻塞主流程"，符合 AGENTS.md 的「优雅降级」原则。
2. **原子写与落盘一致性**：逆向的 `index.json` 原子替换（`pipeline.py:326-328`）、录制回放的 `control.json` 原子替换（`bundle.py:385-387`）与 `manifest.json` 原子写（`manifest.py:63-68`）都用了 tmp + `os.replace`。
