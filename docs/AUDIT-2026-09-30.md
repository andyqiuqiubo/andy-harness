## 零、摘要

本次审计发现三类系统性问题，它们**互相独立**，需要分开处理：

| 类别 | 根因 | 影响面 |
|---|---|---|
| **严重 Bug** | 多用户隔离只做了一半（sessions/memories 做了，attachments/artifacts/traces 没做）；WS 状态机存在双读取竞争；前端用原生 `<img>` 绕过认证头 | 安全越权 + 单用户也会踩的功能失效 |
| **文档失实** | README 把「后端已完成的能力」写成了「用户可用的操作路径」，但前端从未实现对应入口 | 用户按文档操作必然走空 |
| **前后端脱节** | 若干 UI 只写 localStorage；默认值三处不一致；帧结构无类型契约 | 功能「看起来能用」实则无效或静默失效 |

**最需要注意的一点**：README 里那 5 处失实描述（渠道、Computer Use、Jev、断点续跑、用户管理）**全部指向同一个模式**——后端 REST 端点写得完整、有测试、有文档，但前端一行调用都没有。这不是遗漏，更像是「后端先行」的有意分期，但没有在文档和代码里留下「尚无 UI 入口」的标记，导致后续维护者无法判断哪些是「已完成」、哪些是「待接线」。

## 一、严重 Bug

### P0-1｜附件接口完全绕过多用户隔离（跨用户读写文件）

**位置**
- `backend/harness/api/rest/attachments.py:55` — `if not _session_service().get_session(session_id):`
- `backend/harness/api/rest/attachments.py:46-49` — `upload_attachments(session_id, files)` 签名里**没有 `request: Request`**
- `backend/harness/api/rest/attachments.py:135` — `serve_attachment(session_id, att_id)` 同样无 `Request`

**对照正确实现**：`backend/harness/api/rest/sessions.py:17-25`（`_current_user_id`）、`sessions.py:432-435`（`get_session(session_id, user_id=...)`）

**根因**：`backend/harness/infra/repository.py:150-161`

```python
def get(self, session_id: str, user_id: str = "") -> Session | None:
    """获取会话；`user_id` 非空时仅返回归属该用户的会话。"""
    row = self._db.query_one("SELECT * FROM sessions WHERE id = ?", (session_id,))
    if not row:
        return None
    session = self._row_to_session(row)
    if user_id and session.user_id != user_id:   # ← user_id 为 "" 时短路，等于不过滤
        return None
    return session
```

`user_id` 默认值是 `""`，条件 `if user_id and ...` 在空串时短路 → **任何已登录用户都能命中任意会话**。

**复现推理链**
1. 用户 A 登录，会话 S 归属 A（`sessions.user_id = A`）。
2. 用户 B 登录，拿到合法 token（**非管理员同样可以**）。
3. B 发 `GET /api/sessions/S/attachments/{att_id}`。
4. 请求先过 `AuthMiddleware`（`api/middleware/auth.py:76-85`，token 有效 → 放行并注入 `request.state.user`）。
5. 进入 `serve_attachment`（`attachments.py:135`）。该函数**不读 `request.state.user`**，直接 `repo.get(att_id)`（`:137`）。
6. `att["session_id"] == "S"` == 路径里的 `session_id`，通过校验（`:138`）。
7. `FileResponse(att["storage_path"])` 返回 A 的文件字节流。

**影响**
- **数据泄露**：B 可下载 A 上传的任意附件
- **跨用户写入**：B 可用 `POST /api/sessions/S/attachments` 把文件写进 A 的会话
- **提示注入面**：附件内容会经 `modules/attachment/service.py:151` 的 `render_content_parts` 喂给模型

**修复建议**：给两个端点加 `request: Request`，按 `sessions.py:432-435` 的模式校验 `get_session(session_id, user_id=_current_user_id(request))`；`serve_attachment` 应把「不存在」与「无权」统一为 404 语义。

### P0-2｜工件（artifacts）与轨迹（traces）跨用户读写删

**位置**
- `backend/harness/api/rest/artifacts.py:33-45`（list）、`:47-62`（read）、`:64-72`（delete）— 三个端点**均无 `Request`、无 `user_id`**
- `backend/harness/api/rest/traces.py:33-45`（list）、`:47-55`（read）、`:57-65`（delete）— 同上
- `backend/harness/modules/artifact_store/service.py:228-232`（get）、`:266-275`（delete）— 按 `artifact_id` 全局查，无归属校验
- `backend/harness/modules/tracing/service.py`（`get_trace` / `delete_trace`，被 `traces.py:52,62` 调用）— 无 `user_id` 形参

**根因**：`artifacts` 表虽有 `session_id` 列（`infra/database.py:106`），但**所有读写路径都只用 `artifact_id` 定位**。

**影响**
- **机密外泄**：trace 数据包含完整的 prompt 预览、模型输出预览、工具入参（`ws/chat.py:194-207` 上报 `input_preview`/`output_preview`），敏感度远高于普通消息

**修复建议**：`ArtifactStore` / `SpanService` 的读写方法增加 `session_id` 或 `user_id` 参数；REST 层经 `artifacts.session_id` → `sessions.user_id` 两跳关联过滤。





### P0-3｜图片附件在启用认证后必然 401

**位置**：`frontend/src/components/MessageItem.vue:102-108`

```vue
<img
  v-for="att in message.attachments.filter(a => a.kind === 'image')"
  :key="att.id"
  class="msg-attach-img"
  :src="`/api/sessions/${message.session_id}/attachments/${att.id}`"
  ...
/>
```

**根因**：原生 `<img>` 标签**不会携带 `Authorization` 头**，而 `backend/harness/api/middleware/auth.py:76-79` 对所有非豁免 `/api/**` 强制 Bearer：

```python
header = request.headers.get("Authorization", "")
token = header[7:].strip() if header.startswith("Bearer ") else ""
if not token:
    return _unauthorized()
```

**影响**：只要开启认证（README 列为「可选认证多用户」能力），**所有历史图片附件全部裂图**。这是认证功能一旦启用就必然踩到的坑，且用户看到的只是「图片不显示」，很难联想到是认证导致的。

**修复建议**（二选一）
- 前端改用 `fetch + blob:` 生成 objectURL（推荐，不放宽后端）
- 或把该路径加入 `middleware/auth.py` 的 `_PREFIX_PUBLIC` 并改用短时效签名 URL（安全性略低）

### P0-4｜WS 双 `receive_text` 竞争 → 聊天帧静默丢失

**位置**
- 主循环：`backend/harness/api/ws/chat.py:335` — `raw = await websocket.receive_text()`
- 停止监听器：`backend/harness/api/ws/chat.py:486` — `ctrl_raw = await websocket.receive_text()`

**并发证据**：`chat.py:563` `stop_task = asyncio.create_task(_stop_listener())` 与 `chat.py:566` `result = await loop.run(...)` **并发运行**，两个协程在同一 WebSocket 上竞争读取。

**问题**：`_stop_listener` 只处理 `stop`（`:503`）与 `confirm_reply`（`:489`），其余帧全部落进 `:517-518` 的 `except Exception: pass` **静默丢弃**。

**影响**：**单用户也会踩到**。长回答进行中用户追加提问 → 该帧被 `_stop_listener` 抢走 → 消息凭空消失，且无任何错误提示、无重试、无日志（连 `logger` 都没有）。

**修复建议**：改为单 reader 任务统一读取所有入向帧，再按 `type` 分发到 stop 队列 / confirm 队列 / 消息队列，彻底消除竞争。

### P1-1｜权限检查异常时 fail-open，且仅 debug 日志

**位置**：`backend/harness/engine/agent_loop.py:544-553`

```python
except Exception as e:
    logger.debug("权限检查失败（已放行）: %s", e)
    return None   # None = 放行
```

**问题**：权限服务查询失败时**放行工具调用**；同时用的是 `logger.debug`，默认日志级别下**完全不可见**。

**影响**：权限系统任何瞬时故障（DB 锁、插件未加载完成）都会导致本应拦截的高危工具被放行，且故障不可观测、事后无法审计。

**修复建议**：改为 `logger.error`，并对「策略服务不可用」采取 fail-closed，或至少按风险等级区分。

### P1-2｜`user_id=""` 语义等于「不过滤」（fail-open 方向）

**位置**：`backend/harness/infra/repository.py:159`、`:173-175`

**问题**：`user_id` 同时承担「不启用过滤」和「过滤某个用户」两种语义，且**空字符串用户（历史无主数据）与未过滤等价**。

`bootstrap`（`auth_manager/service.py:9-10` 文档所述）把历史无主数据划归首位管理员，但**若 bootstrap 未执行或中途失败**，`user_id=''` 的行对所有用户可见。

**修复建议**：用 `user_id: str | None` 区分三态 —— `None` = 不过滤、`""` = 无主、具体值 = 按用户过滤。
