# andy-harness 项目面试解说

> 用途：面试时主动介绍本项目的话术底稿。建议先讲「3 分钟版本」抓住注意力，再按面试官兴趣深入对应章节。
> 所有数字、技术细节均与仓库实际代码一致，可放心展开。

---

## 一、3 分钟版本（开场主动陈述）

> 我独立开发了一个叫 **andy-harness** 的开源项目——一个**插件化 AI Agent Harness（智能体底座）**，目标是把"让大模型稳定、安全、可观测地干活"这件事工程化。项目从 0 到 1 由我一人完成，后端 Python/FastAPI + SQLite，前端 Vue3 + TypeScript + Pinia，还有 Tauri 桌面壳，目前在 GitHub 开源、准备发布 1.0.0 开发者预览版。
>
> 它的核心能力有五块：
> 1. **Agent 执行环（Agent Loop）**——多轮工具调用、流式输出、人工在环确认（危险操作要人批准）、权限分级、断点续跑（checkpoint resume）；
> 2. **一切皆插件**——工具、技能（Skills）、UI 扩展、渠道（Webhook/Telegram）全部走统一插件契约，热插拔、带权限声明，还有插件市场一键安装；
> 3. **MCP 客户端**——完整实现 Model Context Protocol，同时支持 SSE 和 streamable-http 两种传输，可接入外部工具生态；
> 4. **可观测性**——全链路 Span/Trace 落库、Token 用量统计、长期记忆自动摘要、上下文快照；
> 5. **工程化细节**——多用户认证（PBKDF2 + HMAC 签名）、制品库（大内容自动落盘防 context 爆炸）、定时任务（隔离会话执行）、成本控制（截图去重防图像 token 重复计费）。
>
> 这个项目我全部采用**与编程大模型结对（vibe coding）**的方式完成，所以我对"如何驾驭 AI 写出生产级代码"有一套经过实战验证的方法论，一会儿可以展开讲。

## 二、项目框架（架构讲法）

面试官问"讲讲架构"时，按这个层次讲：

### 2.1 总体分层

```
┌─ 前端 Vue3 + TS + Pinia（含前端 UI 插件体系）
│     │ REST + WebSocket
├─ FastAPI 服务层（按域拆分路由：sessions / agents / plugins / skills / mcp / artifacts / traces / auth ...）
│     │ ServiceRegistry 依赖注入
├─ 模块层（modules/）
│     ├─ agent_loop    执行环：计划→工具→观察→循环→终答
│     ├─ session       会话/消息/上下文快照
│     ├─ tracing       Span/Trace 全链路追踪
│     ├─ artifact_store 制品库（大内容落盘，context 只留引用）
│     ├─ memory        长期记忆 + 定时自动摘要
│     ├─ mcp_client    MCP 客户端（SSE / streamable-http）
│     ├─ auth_manager  多用户认证
│     └─ scheduler     定时任务（每次在隔离会话中执行）
├─ 插件层（plugins/*，plugin.json 声明式契约，启动自动扫描）
└─ 基础设施（infra/：SQLite 数据库、仓库模式、配置）
```

### 2.2 我会着重强调的三个设计决策

**① 一切皆插件**
后端能力全部实现为插件：每个插件一个目录，`plugin.json` 声明 `tool_name / description / parameters_schema / risk_level` 等元数据，启动时自动扫描加载。工具插件声明 `risk_level`，危险操作（如命令执行）自动进入"需人工确认"通道——**安全策略跟着能力声明走，而不是散落在业务代码里**。前端也有一套对称的 UI 插件加载器（`plugin-loader`），后端停用插件，前端界面同步隐藏。

**② 上下文工程是第一公民**
LLM 的 context 窗口是最稀缺资源，所以架构上有三条防线：
- **制品库（Artifact Store）**：超过阈值（默认 6000 字符）的工具输出自动落盘，context 里只留"引用 + 摘要"，需要时按引用取回；
- **上下文快照**：每轮会话的完整状态可序列化、可恢复，是断点续跑的基础；
- **长期记忆自动摘要**：后台定时把历史会话摘要进记忆库，新会话按相关性注入，而不是无限堆历史。

**③ 单 SQLite、零运维**
单机部署场景下用 SQLite + WAL，所有新表 `CREATE TABLE IF NOT EXISTS` 自动升级，老库无需迁移脚本。这是个刻意的取舍：**先保证个人可私有部署、数据完全本地，多实例扩展不在问题域内**。

## 三、核心技术点（可挑 3-4 个深入）

| 技术点 | 一句话讲法 | 面试官可能追问的点 |
|---|---|---|
| Agent Loop 状态机 | 流式 WS 驱动的多轮工具调用环，支持 stop / 人工确认 / 预算控制 | 如何防死循环（工具调用上限 + 强制终答） |
| 人工在环（HITL） | `risk_level` 高的工具先挂起，前端弹确认框，用户批复后继续 | 挂起期间的状态怎么存、超时怎么处理 |
| 断点续跑 | 每轮迭代后 best-effort 写 checkpoint，`POST /runs/{id}/resume` 基于持久化上下文继续 | 为什么"会话历史即完整状态快照"（不重放内存态） |
| MCP 双传输 | 一个客户端同时兼容旧版 SSE（GET 建流拿 endpoint）和 streamable-http（POST 直连、解析内联 SSE） | 协议演进期如何做兼容层 |
| 认证设计 | PBKDF2 口令哈希 + HMAC 请求签名，WS 用 `?token=` 握手，401/1008 统一处理 | 为什么不引 JWT 库（可控、无外部依赖、密钥落盘 0600） |
| 多用户隔离 | 所有资源按 `user_id` 两跳过滤（资源→session→user 的 JOIN） | 归属校验放在哪一层（REST 层校验 + 存储层过滤） |
| 截图成本控制 | Computer Use 场景下截图不逐轮累积进 context，防图像 token 重复计费 | 多模态 token 成本量化 |
| 前端插件化 | 运行时加载 UI 插件、与后端插件启停状态双向同步 | 微前端思路的轻量替代 |

## 四、难点与解决（最有面试价值的部分）

> 讲难点要讲"现象 → 定位过程 → 根因 → 方案 → 防回归"。以下都是真实发生、仓库里有代码和测试佐证的案例。

### 难点 1：WebSocket 双 reader 竞争导致控制帧丢失（并发 Bug）

- **现象**：用户点"停止"偶尔无响应；人工确认的回复偶尔不被兑现。
- **定位**：审查代码发现 WS 消息循环里有两个并发协程都在调 `receive_text()`——一个处理聊天消息、一个监听 stop 控制帧。帧到达时被谁抢到是随机的。
- **根因**：WebSocket 是有序字节流，**多个并发 reader 会让帧的投递目的地不确定**。
- **方案**：重构为**单 reader 架构**——唯一的读取协程按帧类型分发到 `message_queue` 和 `control_queue` 两个队列，再由 dispatcher 协程分别消费。主循环只从 message_queue 取帧。
- **防回归**：补了"stop 帧必达"的回归测试。
- **面试加分点**：这类 bug 的通用教训——"**一个连接一个 reader**"，所有事件驱动的消息循环都适用。

### 难点 2：共享单例被 monkey-patch 导致跨会话内容泄漏（严重级）

- **现象**：压测时发现 A 用户的流式回答偶尔出现在 B 的连接里。
- **定位**：WS 层为了加流式包装，直接 `provider.chat = wrapper` 改了 provider 实例——而 provider 是**按 id 缓存的全局单例**，并发连接反复互相包装，行为不可预测。
- **根因**：对共享可变对象做运行时补丁。
- **方案**：设计了一个 `_StreamingProviderProxy`（`__getattr__` 委托 + 覆写 `chat`），**每个连接拿自己的代理，真实实例永远不可变**。
- **面试加分点**：总结成原则——"**给共享对象加行为，用组合/代理，永远不要改实例属性**"。

### 难点 3：MCP 协议演进期的传输兼容

- **现象**：接入某远端 MCP server 一直报"尚未获得 POST endpoint"。
- **定位**：用 `curl` 直接对远端发 initialize 请求，发现它对 GET 返回 405——远端已迁移到 streamable-http 形态，而配置类型仍写的 `sse`。
- **方案**：客户端做成**自适应**：先按标准 SSE 走 GET 建流；收到 405 自动降级为 POST 直连（把配置 URL 当 JSON-RPC 端点），并兼容响应体内联 SSE。本地写了两个 echo server 分别模拟两种形态做回归。
- **加分点**：**遇到协议问题先 curl 复现最小请求，区分"服务端问题"和"客户端形态不匹配"**，不要盲改代码。

### 难点 4：「工具连上了但模型不用」

- **现象**：接入外部 MCP 工具后，模型总是用内置工具，不用外部工具。
- **定位**：查 spans 表还原当时 run 的实际工具调用，发现外部工具 description 只有一句英文，且没写参数格式。
- **根因**：MCP 工具只以 function 定义注入，系统提示不点名；**模型选工具靠 description 质量**。
- **方案**：系统提示按 server 生成"外部能力目录"并要求优先调用；工具描述头部拼接 server 配置里的中文能力说明与参数约定。
- **加分点**：这是典型的 **agent 工程问题而非模型问题**——工具的 description 就是给模型看的 API 文档。

### 难点 5：测试基建被开发环境的安全机制"劫持"

- **现象**：几百个测试在 fixture 阶段集体 ERROR，报 `OSError: 找不到网络路径`。
- **定位**：pytest 临时目录收尾时的 `shutil.rmtree` 被 IDE 注入的 safe-delete shim 接管走了回收站；而 shim 的"OS 临时目录 bypass"用 `tempfile.gettempdir()` 的 **8.3 短路径**与真实**长路径**做字符串比较，永远不相等。
- **方案**：用环境变量关闭 shim + 显式指定 basetemp；测试内每个用例独立临时库（还顺带解决了 SQLite `database is locked` 的跨用例锁竞争）。
- **加分点**：**环境特异性故障要读 shim/中间层的源码**，而不是反复重试。

### 难点 6：启用认证后所有图片附件破图

- **现象**：开启 Bearer 认证后，历史消息里的图片全部 401。
- **根因**：`<img src>` 是浏览器原生请求，**带不上 Authorization 头**。
- **方案**：封装 `fetch + blob:` 的渲染组件（fetch 可带认证头，成功后 `URL.createObjectURL` 渲染、卸载时 revoke），失败回退直链，单用户模式行为不变。
- **加分点**：HTTP 认证里经典的 "`<img>` 不带 header" 问题，移动端/小程序也有同款。

### 难点 7：跨团队协作式的"AI 审计 AI"

让另一个 AI 对项目做安全审计后，我**逐条对照源码核验**它的报告：它报了 4 个"P0 级数据泄露"，我核验后确认其中代码层面属实（附件/工件/轨迹缺归属校验），但**严重度被高估**——因为默认部署是单用户、认证默认关闭，跨用户泄露在默认配置下不成立。最终全部按"防御性修复"落地且保证单用户行为零变化，同时在审计结论里明确写下了不认同的理由。
**加分点**：对 AI 产出**既不盲信也不盲弃**，用源码核验 + 部署语境评估严重度——这正是"AI 时代工程师的核心价值"。

## 五、如何与大模型 Vibe Coding（方法论，面试官最常问）

> 核心观点：**vibe coding 不等于"AI 写代码我来改"**，而是"我把工程判断结构化地喂给 AI，把执行外包，把决策留下"。我在这个项目里沉淀了六条实践：

### 1. 用"文档驱动"代替"聊天驱动"
需求不是打字聊出来的，而是先写成 `ENHANCEMENTS.md`（P0/P1/P2 分级的增强清单）、`GAP-ANALYSIS.md`（现状-目标差距分析）。每次会话让 AI 读文档再动手，**跨会话上下文零损耗**，优先级我自己定。

### 2. 把"验证四关"写成铁律
每一项能力必须过：pytest 全量 → ruff + mypy 静态门 → HTTP 冒烟脚本 → 前端 vue-tsc + vite build。这四条直接写进项目记忆文件，AI 每次都会自己跑。**AI 的代码质量 = 你给的验收门槛**。

### 3. 让 AI 之间互审
一个 AI 写功能，另一个 AI 做审计（产出安全/质量报告），我再逐条核验。实践发现：AI 审计对"代码层缺陷"很准（如归属校验缺失、并发竞争），但对"严重度评估"容易脱离部署语境夸大——**事实交给 AI，判断留给人**。

### 4. 项目记忆文件（MEMORY.md）沉淀约定
踩过的坑（如 Vite 解析无扩展名 import 时 `.js` 影子文件优先于 `.ts`、TS 配置禁止构造函数参数属性）都写成记忆条目，新会话自动注入，**同一个坑不踩第二次**。

### 5. 定位问题时"先最小复现，再让 AI 动手"
curl 最小请求复现 MCP 协议问题、查 spans 表还原 run 的工具调用轨迹——**我把"证据"喂给 AI，让它在证据上推理**，而不是让它猜。

### 6. 人类负责的三件事
架构决策（为什么单 SQLite）、安全边界（哪些操作必须人工确认）、严重度判断（P0 还是 P2）。其余——写代码、写测试、查 lint、写文档——全部外包给 AI。
**一句话总结：我把工程师的角色从"码农"升级成了"给 AI 立规矩的技术负责人"。**

## 六、可能的追问 & 建议答法

**Q：为什么后端选 FastAPI + SQLite，不上 PostgreSQL？**
单机私有部署是第一需求，SQLite 零运维、数据就是一个文件、备份即复制。用仓库模式隔离了存储层，真要换 PG 只动 infra。**选型的第一原则是匹配问题域，不是简历好看。**

**Q：Agent 怎么防失控（死循环/费用爆炸）？**
四层：工具调用上限 + 达到上限强制终答；token 预算控制；制品落盘防 context 膨胀；危险操作人工确认。另有一次性的"成本审计"实践——发现截图类多模态内容逐轮累积会平方级重复计费，做了去重与降本策略。

**Q：多用户安全做到什么程度？**
认证（PBKDF2+HMAC）、授权（资源归属两跳校验）、审计（全链路 trace）。同时我很清楚边界：默认单用户模式下认证是关闭的，所以文档明确标注"面向本机/可信网络部署"，不夸大安全声明——**准确陈述边界本身就是安全素养**。

**Q：这个项目最花时间的地方？**
不是功能，是**回归**：每次加能力都可能破坏既有行为，所以测试基建（fixture 隔离、临时库、冒烟脚本）和静态门是投入产出比最高的部分。

**Q：一个人 + AI 干，如何保证质量不是"幻觉式自信"？**
测试说了算 + 我不信任没有证据的结论（包括 AI 的），关键结论我都在源码/数据里核验过。项目里的每一个"已修复"都有对应测试或验证记录。
