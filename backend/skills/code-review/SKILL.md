# 代码评审

## 流程

1. **先定位范围**：确认要评审的是哪段代码 / 哪个 diff / 哪个 PR。范围不清就先问一句，不要假设。
2. **读懂意图**：先看这段代码想解决什么问题（提交信息、PR 描述、相关 issue），再评价实现。没读懂意图前不下结论。
3. **通读一遍再提问题**：不要边读边输出，避免重复和误判。
4. **分级输出**（见下方格式）。
5. **给出可执行的修改示例**，而不是只说"这里不好"。

## 评审维度（按重要性排序）

1. **正确性**：逻辑错误、边界条件、空值/异常路径、并发与竞态、资源泄漏。
2. **安全性**：注入（SQL / 命令 / XSS）、越权、敏感信息泄露、依赖的已知漏洞。
3. **可维护性**：命名、函数长度与职责、重复代码、魔法数字、错误处理是否一致。
4. **性能**：N+1 查询、循环内的重复 IO、不必要的全量拷贝、热点路径的复杂度。
5. **测试**：改动是否覆盖关键路径，边界用例是否缺失。

## 输出格式

```markdown
## 评审结论
一句话总结：这段代码能否合入，主要风险是什么。

## 阻塞（必须改）
- `文件:行号` 问题是什么 / 为什么 / 怎么改（附代码片段）

## 建议（强烈推荐改）
- `文件:行号` 问题 + 建议改法

## 可选（看情况）
- `文件:行号` 可选的改进点

## 做得好的地方
- 值得保留的写法（可选，但能提升协作体验）
```

## 硬性要求

- 每条问题必须带**文件与行号**（或 diff 位置），否则无法定位。
- 只报你**确认**的问题；不确定的用"疑似"标注并说明判断依据。
- 不要为了凑数而输出。没有阻塞问题就直说"可以合入"。
- 区分"风格偏好"和"真实缺陷"：前者归入可选，或明确说明是个人偏好。
- 若代码整体质量很差需要重写，说明理由并给出重写方案，不要逐行挑刺。
